Escalation lookup trusts the client-supplied studio id

app/api/escalation/route.ts:64 +2 more: route.ts:98, service.ts:31

Problem

The handler reads studioId from the request body and passes it straight to the query. A member of studio A can post studio B's id and read B's escalation thread, because the row filter never re-derives the id from the session.

Decision

Either derive studioId from the session and ignore the body field (breaks the admin impersonation path that currently relies on it), or keep the field and gate it behind the existing admin claim check.

Config writes merge instead of replacing, unlike every sibling route

app/portal/config/actions.ts:112

Deviation

docs/portal-config.md specifies a full replace, and the three sibling routes replace. This one shallow-merges, so a removed key survives.

Case for the current behaviour

Merging keeps older clients working: they post partial payloads and would otherwise wipe fields they never knew about. The spec predates those clients.
